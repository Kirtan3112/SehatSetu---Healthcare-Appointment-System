Healthcare Appointment System — Suitable
Process Model and Why
 Oct 13, 2026  ·  @Hunny
1. Chosen Model
The best-suited process model is Agile (Scrum) with iterative, incremental delivery: 2-
week sprints, each ending in a working, tested increment of the system. A short upfront
phase fixes the architecture, database schema and roles; features are then delivered
sprint by sprint.
2. Why Agile Fits This Project
Modular features: the system splits cleanly into auth, doctor management, slots,
booking, notifications and admin, so each can ship and be tested on its own.
Three user groups: patients, doctors and admins can review each increment early, so
usability problems surface before the whole system is built.
Evolving requirements: reminders, rescheduling rules and dashboards usually change
after users see them; short sprints absorb that change cheaply.
Early risk reduction: the hardest technical problem, double-booking under concurrent
load, is built and load-tested in an early sprint rather than at the end.
MERN fits iteration: React components, REST endpoints and Mongoose schemas are
easy to change and redeploy, and CI/CD supports frequent releases.
Small team: daily stand-ups, sprint reviews and a shared backlog suit a team of 3 to 6
developers with little overhead.
Quality: testing happens inside every sprint, so defects are found while the code is still
fresh.
3. Alternatives Considered
Model Strength Why it is less suitable here
Waterfall Simple, well documented Needs all requirements frozen upfront;
user feedback arrives only at the end
V-Model Strong verification Rigid and sequential; costly when
requirements change

1. Overview and Verdict
The Healthcare Appointment System is technically feasible with the MERN stack, using
only mature, open-source tools and no specialised hardware. It serves three roles
(patient, doctor, admin) through one React web app backed by a REST API and MongoDB.
The hardest technical problem is preventing double-booking under concurrent requests,
which MongoDB's unique indexes and atomic updates solve. This document covers
technical feasibility only.
2. Technology Stack
Every component below is free, widely documented and production-proven.

7. API Request Handling and High-Concurrency Pipeline
A Node.js cluster can serve 1,000 concurrent users comfortably when requests pass
through a load balancer, a token-bucket rate limiter, cache-aside reads, an atomic slot
claim and a background job queue. Assuming 1,000 users each send one request every 5
seconds, peak load is about 200 requests per second; this is an estimate to confirm by
load testing.
Load balancing: Nginx with least-connections routing across 3 or more stateless API
instances (PM2 cluster mode or Docker replicas); health checks remove failing
instances.
Rate limiting: token bucket per user and IP, stored in Redis (for example, a burst of 20
and a refill of 5 per second); excess requests get 429 with a Retry-After header.
Cache-aside reads: doctor lists, specializations and slot availability are cached in Redis
for 30 to 60 seconds; the slot cache is cleared on every booking.
Accuracy under concurrency: the slot claim is an atomic compare-and-set
( findOneAndUpdate  where isBooked is false), backed by the unique slot index; an
idempotency key on booking requests prevents duplicates when a client retries.
Asynchronous work: confirmations and reminders go to a BullMQ queue with retries
and exponential backoff, so the API responds first.
Overload protection: MongoDB connection pooling, 5-second request timeouts, a
circuit breaker on email/SMS, body-size limits, pagination and gzip. If the system
saturates, it returns 503 (load shedding) instead of queuing without limit.
request pipeline · 4 gates, cache, atomic claim, job queue

9. Security
Authentication: bcrypt-hashed passwords; short-lived JWT access tokens with
refresh tokens in httpOnly cookies; account lockout and rate limiting on login
Authorization: role-based middleware (patient, doctor, admin) on every route; users
can access only their own records
Transport and data: HTTPS/TLS everywhere; MongoDB encryption at rest; secrets in
environment variables
API hardening: Helmet, CORS whitelist, input validation, NoSQL-injection sanitising
(express-mongo-sanitize), XSS protection
Privacy: minimal medical data stored; where applicable, align with regulations such as
HIPAA or GDPR (consent, deletion, access logs)
Monitoring: audit logs, error logging (Winston), automated daily backups
10. Resource Requirements
Hardware (development): laptop with 8 GB RAM or more, modern browser; no special
hardware
Software: VS Code, Node.js LTS, MongoDB Atlas free tier, Postman, Git, Docker
Team skills: React, Node/Express, MongoDB, REST design, basic DevOps and testing
Production: one app server (2 vCPU, 4 GB RAM is enough to start), managed MongoDB
cluster, domain and SSL certificate, email service
